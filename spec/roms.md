# ROMs

Anchorage finds the user's own ROM files and hands the right one to each port. It never downloads or distributes ROMs.

## Requirements

|----|-------------|--------|-------------|
| `ROM-1` | The ROM folder is `[roms] directory` (`CONF-8`), else the folder chosen in the app (`ROM-12`), else the one found by `ROM-10`, with `~` expanded. A missing or unreadable folder is a normal state ("ROM folder not found"), not an error. | done | `test_roms` (missing folder gives status "missing"; `expand_dir`) |

## Implementation notes

- `app/src/roms.gd` does scanning, hashing and preparing; `ports.gd` owns the thread and the cache.
- `app/src/rom_folders.gd` finds the folder (`ROM-10`, `ROM-15`, `ROM-16`), lists folders for the chooser and searches the drives (`ROM-14`) as pure functions over a home, a media folder and the mounts text, so tests use fake trees; `ports.gd` runs them on the worker pool (detection, listings) or a `SearchJob` thread.
- The chooser (`app/scenes/rom_folder.tscn`, `app/src/ui/rom_folder.gd`) opens over the home screen. Starting points are on the left; the D-pad's left and right move between them and the folder list.
- Godot's `ZIPReader` reads zip entries, and `HashingContext` computes SHA1. Byte order is detected from the first four bytes of the data: `80 37 12 40` is z64, `37 80 40 12` is v64, `40 12 37 80` is n64.
- A ROM is at most 64 MiB, so holding one in memory while hashing is fine.

## EmuDeck and RetroDECK

- Research with sources and what could not be verified: [docs/research/emudeck-retrodeck.md](../docs/research/emudeck-retrodeck.md). Read in the tools' source since: EmuDeck's `vars.sh` sets `emudeckFolder="$HOME/.config/EmuDeck"` and its settings are written unquoted with `$HOME` already expanded; RetroDECK keeps `retrodeck.json` in `$XDG_CONFIG_HOME/retrodeck/` (inside the Flatpak, `~/.var/app/net.retrodeck.retrodeck/config/retrodeck/`) and converts an old INI `retrodeck.cfg` (`[paths]` with `rdhome`, `roms_folder`) to it. Unverified and therefore checked on a real Deck before release: the exact SD card mount name on current SteamOS. The parsers accept every variant listed, so a wrong guess costs a fallback to the next step, not a failure.
- Mounts come from `/proc/self/mounts` (mount points under `/run/media` with their device, so a `/dev/mmcblk*` mount is the SD card whatever its path) and from the folders under `/run/media` (a device-named folder such as `mmcblk0p1` is a mount; any other folder, such as `/run/media/deck`, holds mounts). The SD card search (`ROM-14`) counts a mount's own folder as level 0 and goes four levels below it. Results are in mount order (SD card first), and within a mount folders named `n64` come first, then shallower before deeper, then by path. The search that runs by itself (`ROM-10`) uses the first result.
- A folder found by `ROM-10` is not stored: it is looked for again at each start. Only a folder the user chose is stored (`ROM-12`).
- The chooser lists folders through `Ports` (`PORT-14`), which reads them on the worker pool.
- Both tools use the ES-DE folder names, so the N64 folder is `n64` in both.
