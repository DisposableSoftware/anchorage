# Updating Anchorage

Anchorage updates its own AppImage from Game Mode, so a user never has to go back to Desktop Mode and the installer script. The release that carries the new AppImage is the one `scripts/release-assets.sh` stages (`INT-25`, `INT-28`).

## Requirements

| ID | Requirement | Status | Verified by |
|----|-------------|--------|-------------|
| `UPD-1` | Self-update applies only when Anchorage runs from an AppImage (`APPIMAGE` names an existing file the user can write, in a folder the user can write). From anything else (a Nix build, a checkout, a read-only file) the app shows `Updates come from how you installed it` in place of the update entry (always, as a line that takes no focus), never looks for a release and never touches a file. | planned | `test_self_update` (fake `APPIMAGE` paths: writable, read-only, unset) |
| `UPD-2` | Anchorage checks `https://api.github.com/repos/DisposableSoftware/anchorage/releases/latest` for a release newer than its own version (`application/config/version`, compared as numbers: `0.10.0` is newer than `0.9.0`; never a downgrade, never a prerelease or draft). The check runs at start when `[ports] check_updates` is not `false` (at most once an hour, with the port checks), and on `refresh` and the menu entry (`UPD-4`) always. A failed check shows nothing worse than being offline. | planned | `test_self_update` (fake releases: newer, same, older, prerelease, `0.10.0` vs `0.9.0`, failure) |
| `UPD-3` | When a newer release exists, the home screen shows it without taking over: a `Update 0.3.0` chip in the bottom bar next to the name (`Restart for 0.3.0` once it is swapped in, `UPD-9`), and a toast `Anchorage 0.3.0 is available` once per version per session. The `Update Anchorage to 0.3.0` entry is the first entry of the app menu (`HOME-14`). | planned | `test_home`; screenshot |
| `UPD-4` | Choosing the entry downloads `Anchorage-<version>-x86_64.AppImage` and `SHA256SUMS` of that release (GitHub release assets of `DisposableSoftware/anchorage` only, over HTTPS, the redirect rules of `PORT-13`) next to the running AppImage as `Anchorage.AppImage.new` (the AppImage's own path plus `.new`), in a dialog with progress and cancel (`back`), never blocking the main loop. It starts only when the folder has room for the download and the kept copy (`UPD-6`). The size is at most 200 MiB and must match the release's `size`; the SHA-256 must match the line for that file in `SHA256SUMS` and the asset's API `digest` when the release lists one. A mismatch deletes the download and shows `Could not update “Anchorage”` with the reason. | planned | `test_self_update` (fake HTTP: success, bad hash, wrong size, missing line, cancel, foreign host) |
| `UPD-5` | Before it replaces anything, Anchorage checks that the download is an AppImage that starts: the ELF header, the AppImage type 2 magic, the executable bit set, and `--appimage-version` answering with status 0 within 10 seconds. A download that fails any of these is deleted and the running AppImage stays untouched. | planned | `test_self_update` (fake files: not ELF, no magic, a script that hangs, one that fails) |
| `UPD-6` | The swap is a single `rename` of `Anchorage.AppImage.new` over the AppImage path, so the running copy keeps working and a power loss leaves either the old file or the new one, never a partial one. The old file is first copied to `Anchorage.AppImage.previous` (the path plus `.previous`, so the path never goes missing), and the copy is kept until the new version has run for 10 seconds, then deleted, and the next start removes a stale one. The Steam shortcut, its ID and artwork stay valid because the path does not change. | planned | `test_self_update` (rename semantics on temp files, previous cleanup) |
| `UPD-7` | The installer's record of the files it wrote (`~/.local/state/anchorage-installer/files.sha256`, `INT-33`) is updated with the new AppImage's hash after a swap, on the line that names this file with the old file's hash (a line with another hash means the user replaced the file, and stays), so a later `install-steamos.sh` rerun sees the same version as current and `--uninstall` still removes the file. | planned | `test_self_update` (record before and after); `scripts/manual/steam-install.sh` (a rerun after a self-update changes nothing) |
| `UPD-8` | No update starts or swaps while an install, an update or a launch is busy, or while a port is running; the entry says `Finish what is running first` and the download waits for the queue. The update never touches ports, their data or the state. | planned | `test_self_update` (busy and running ports) |
| `UPD-9` | After the swap Anchorage offers `Restart now` and `Later`. `Restart now` starts the new AppImage with a detached `/bin/sh` that waits for this process to end (same environment, no AppImage variables of the old process), then quits cleanly. If Steam counts the app as ended, opening it again from the library works, and the dialog says so. `Later` leaves the new version for the next start. | planned | `test_self_update` (the spawned command line and environment); manual on a Deck |
| `UPD-10` | The release notes of the newer version are not fetched or shown (the chip and the entry name only the version number), so no text from a release is rendered by the app. | planned | `test_self_update` |

## Implementation notes

- `app/src/self_update.gd` holds the logic (check, download, verify, swap, restart command) so it can be tested with fake HTTP and temp files. `main.gd` adds it next to `Ports` (`ports.gd` stays untouched: it is at gdlint's 1000-line limit) and hands it to the home screen as `home.self_update`; with `--fake-ports` it adds `app/src/self_update_fake.gd` in the scenario's state (`self-update`, `self-busy`, `self-downloading`, `self-ready`, `self-unsupported`). Screens use `info()`, `check(manual)`, `start()`, `cancel()`, `restart()` and the `changed` signal. `info()` is `{state, version, current, progress, detail, error, blocked}`; `state` is `unsupported`, `none`, `available`, `waiting`, `downloading`, `verifying`, `ready` or `failed`.
- `UPD-8` reads the ports through the screens' own interface: any `ports.info(id)` with a `busy.action` or `running` blocks.
- The last check's time and the newest version it found are kept in `$XDG_STATE_HOME/anchorage/self-update.ini` (`[anchorage] last_check`, `latest`), beside `state.ini` but apart from it, so the ports' state is never written by the update; the chip shows again at the next start within the hour without a request.
- The running AppImage is a mounted squashfs (or an extraction directory under `APPIMAGE_EXTRACT_AND_RUN`); replacing the file by `rename` does not disturb it. Never write into the file in place. Before the rename `sync` flushes `.new` and `.previous`; after it, the folder and the record.
- Trust is the same as for the port catalog (`spec/ports.md`, "Catalog updates"): a release of this repository, over HTTPS, checked against its own `SHA256SUMS` and the API digest. That guards against corruption and a wrong download; it does not protect against a malicious release.
- A self-update replaces only the AppImage. Steam artwork, the desktop entry and the installer script change only when the installer is run again.
- `--appimage-version` is answered by the AppImage runtime alone, before it mounts anything: it proves the file is a working runtime with a payload attached, not that the new Anchorage starts. On a host with an AppImage binfmt handler (NixOS's `programs.appimage.binfmt`) the kernel hands the file to `appimage-run`, which starts the app instead, so the check fails after 10 s there; SteamOS has no such handler.
- **Test hook.** `ANCHORAGE_RELEASES_URL` replaces the `releases/latest` URL, for tests only. It is used only when it is a plain `http://127.0.0.1:<port>/` URL, and then the release's asset URLs must be on that same origin; anything else is ignored. `scripts/manual/self-update.sh` uses it.

## What can go wrong (adversarial review, 2026-11-24)

- **A malicious release** (someone who can publish a release of this repository) runs its code: at the `--appimage-version` check already, and as Anchorage from the next start. SHA256SUMS and the digest come from the same release, so they prove only that the file is the one published. The 200 MiB cap, the exact asset URLs (`https://github.com/DisposableSoftware/anchorage/releases/download/<tag>/<name>`, redirects only to GitHub's hosts) and the ignored release text (`UPD-10`) limit what a release that is merely broken or a look-alike URL can do; they do not stop a malicious one. The check run is killed after 10 s, but only its own process: anything it forks keeps running.
- **A broken release** that is a valid AppImage but whose Anchorage crashes passes `UPD-5` and is swapped in. `.previous` stays while the new copy never runs 10 s, so the way back is Desktop Mode: `mv ~/Applications/Anchorage.AppImage.previous ~/Applications/Anchorage.AppImage`, or the installer's copy of the older release (`.../download/vX.Y.Z/install-steamos.sh`; the latest one would install the broken one again). There is no automatic rollback. One that runs 10 s and fails later has lost `.previous`.
- **A half-finished update.** A download cut off leaves `.new`; the next start deletes it once it is 10 minutes old (younger, it may be another Anchorage's download), and every update deletes it before it starts. A cut-off copy to `.previous` is a partial file whose hash matches nothing, so it never changes the record, and the next start deletes it. A stray `files.sha256.anchorage-self-update` or `self-update.ini.tmp` from a cut-off write is left behind, harmlessly.
- **Power loss between steps.** Before the rename the path holds the old file, after it the new one (one `rename`, `sync` first; ext4's `auto_da_alloc` also flushes a file renamed over another). Between the rename and the record update, the record names the old hash: the next start sees `.previous`, and when the record's line holds `.previous`'s hash it puts the current file's hash there (`recover_record`), before it deletes `.previous`.
- **Other filesystems.** `~/Applications` is on the Deck's internal ext4. On exFAT or FAT (an AppImage run from the SD card) `rename` over an existing file works on Linux but is not journaled, so a power loss mid-rename may lose both names; permissions come from the mount options, so the write check (`UPD-1`) and the executable bit follow `fmask`, and a `noexec` mount fails the check run (exit 126) and changes nothing. Not tried on a real exFAT card.
- **Disk full.** The update starts only with room for the download, the copy and 16 MiB. A disk that fills meanwhile fails the download or the copy, which deletes the partial file and keeps the AppImage. A failed record write leaves the old hash: the AppImage then counts as not the installer's (`--uninstall` keeps it, a rerun re-installs the release).
- **Two Anchorages at once** share `.new`: the hash check refuses a file the other one changed, and the swap refuses a download that is no longer the checked one.
- **Only a Deck can confirm:** the FUSE-mounted AppImage being renamed over while it runs (the e2e used extract-and-run), whether Steam keeps tracking the restarted copy (it is a grandchild of the process Steam started, reparented to Steam's reaper) and whether gamescope shows its window, and the real GitHub redirect chain for a release asset.
