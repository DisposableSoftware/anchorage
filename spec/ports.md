# Ports

How Anchorage finds, installs, updates, launches and removes the HarbourMasters ports. Facts about each port (asset names, ROM lookup, environment variables) come from reading the ports' releases and source; the research is summarised in the implementation notes. Where a fact could not be run on a real machine, it says so.

## Implementation notes

- **Service contract.** `app/src/ports.gd` (`Ports`, a `Node`) is created by `main.gd` and handed to screens. Screens read `ports.list() -> Array` of port ids in catalog order and `ports.info(id) -> Dictionary` with these keys: `id`, `name`, `game`, `monogram` (the catalog's, or `""`), `description`, `installed` (bool), `installed_version`, `latest_version` (empty when unknown), `update_available` (bool), `offline` (bool), `rom` (`{found: bool, label: String, path: String, wanted: Array[String]}`; `wanted` names the game versions the port accepts), `busy` (`{action: "install"|"update"|"remove"|"launch"|"scan"|"", progress: float, detail: String}`; `progress` is 0..1 or -1 when unknown), `running` (bool), `first_run` (the catalog's first-launch note while the port has no archive, else `""`: `PORT-17`), `art` (the cover art as a `Texture2D`, or `null` while there is none: `art.md`), `error` (`""` or a `Could not <verb> "<name>"` message with detail), `is_new` (a port a catalog fetch added, not focused yet: `PORT-23`). Screens call `ports.install(id)`, `update(id)`, `remove(id)`, `launch(id)`, `cancel(id)`, `refresh()` (catalog, updates and ROM rescan), `mark_seen(id)` and `dismiss_error(id)`. `Ports` emits `changed(id)` whenever `info(id)` changes, , `launched(id)` and `exited(id)`, and `notice_changed` (`notice()`, `PORT-23`). A `ports_fake.gd` with the same interface and fixed demo data serves screenshots and UI tests.
  The ROM folder (`ROM-10` to `ROM-16`): `ports.rom_folder_info() -> {path (shown with ~), full, source ("config"|"chosen"|"emudeck"|"retrodeck"|"default"|"mount"|"search"|"fallback", or "" while it is being found), locked (config.ini sets it), config_file}`; `ports.set_rom_folder(path)` stores the choice and rescans (nothing while locked); `ports.browse(path)` lists a folder off the main loop and answers with `folder_listed(path, {ok, path, roms, folders: [{name, path, roms}], places: [{label, path, sd}]})` (an empty path lists the ROM folder); `ports.search_sd_card()`, `ports.cancel_search()` and `ports.search_info() -> {status: "idle"|"running"|"done"|"no_card"|"cancelled", results: [{path, display, label, folder, roms}]}`, with `search_changed` on every change; `rom_folder_changed` fires when the folder changes.
- **Layout under `user://`** (`$XDG_DATA_HOME/anchorage/`): `ports/<id>/current/`, `previous/`, `download/`, `data/`. While an install runs, `download/` holds the downloaded asset and the unpacked new version (`download/staging/`), which is renamed to `current/` at the end. `cleanup_stale` also puts `previous/` back as `current/` when a kill came between the two renames of a swap.
- **Catalog schema** (`app/data/ports.json`, documented in the header of `app/src/catalog.gd`): `schema`, `version` (see "Catalog updates") and one object per port in `ports`:
  - `id`, `name`, `game`, `description`, `repo` (`owner/name`), `asset_suffix` (matched without case against the asset name).
  - `archive`: the generated archive names; the port counts as extracted when any exists.
  - `launch`: `executable` (path inside `current/`; a bare AppImage is saved under this name), `cwd` (`data` or `current`), `args`.
  - `first_run` (optional): a short note for the detail panel, shown until the port has made its archive (`PORT-17`).
  - `monogram` (optional): the card's short name when it is not the one built from the title (`PM64`, `BK`; see the home screen notes). `info.monogram` passes it on, `""` when absent.
  - `extra_files`: paths of files or folders inside the unpacked release that install copies into `data/` (`PORT-10`), and launch copies again when missing (`PORT-9`).
  - `rom_place` (`data_dir`, `cwd` (the launch working directory) or `argv` (the data folder, and the path passed as an argument: `PORT-16`)), `rom_file` (name of the written big-endian ROM, ending in `.z64`) and `roms`: a list of `{label, sha1}` in priority order (`ROM-7`). A bad entry is dropped with a warning, never a crash.
- **Update checks.** The automatic check at start runs when `[ports] check_updates` is not `false` and the last successful check is at least one hour old (or in the future, or missing). The `refresh` binding is the user asking, so it always checks. A check that no port answered does not count as a check. Release downloads are redirected to a CDN: `http.gd` follows redirects by hand, downloads and API calls alike, and accepts only https hops on GitHub's hosts whose host part is a plain name (`PORT-13`). Downloads are polled from the main loop, not on `HTTPRequest`'s thread: that thread blocks in a socket read, and cancelling a stalled download (which joins it) froze the app. A repo that GitHub has moved is followed for the API call only, so the catalog must name the current `repo`, or the asset URL is refused.
- **What the research found** (read from the latest releases, 2026-11; nothing below was run on a Deck):
  - Shipwright 9.3.1 ships a bare `.appimage`; 2ship2harkinian 5.0.1, Starship v2.0.0 and SpaghettiKart 1.0.0 ship `*-Linux.zip` or `spaghetti-linux.zip` holding an `.appimage` and extra files. Codenames change per minor version, so match on a suffix. The AppImages need `libfuse.so.2` or `APPIMAGE_EXTRACT_AND_RUN=1`.
  - No port reads a ROM from a zip. SoH and 2ship byte-swap `.v64` and `.n64`; Starship and SpaghettiKart need big-endian `.z64`. So Anchorage always writes `.z64`.
  - SoH and 2ship scan their data folder for ROMs and treat every command-line argument as a ROM path. SpaghettiKart scans the current directory for `*.z64`. Starship v2.0.0 only has a file picker for the ROM and reads `config.yml` and `assets/` from the current directory and writes `sf64.o2r` there, so its catalog entry copies both into the data folder (`extra_files`) and runs it there (`cwd: data`). A fully unattended first extraction is not possible for Starship, and all ports may show a popup. The catalog states, per port, how the ROM is handed over; Starship's first run is a known gap (`PORT-9`).
  - `SHIP_HOME` sets the data folder on Linux for all four. Generated archives: `oot.o2r` (and `oot-mq.o2r`), `mm.o2r`, `sf64.o2r`, `mk64.o2r`.
  - Asset digests (one unauthenticated `releases/latest` call per repo, 2026-11-23): Shipwright 9.3.1, 2ship2harkinian 5.0.1 and SpaghettiKart 1.0.0 list `"digest": "sha256:<64 hex>"` for every asset; Starship v2.0.0 (May 2025, older than GitHub's digests) lists `"digest": null`, so for it only the size is checked. Each release has exactly one asset matching its suffix (`SoH-Dewey-Bravo.appimage`, `2Ship-Battler-Bravo-Linux.zip`, `Starship-Barnard-Alfa-Linux.zip`, `spaghetti-linux.zip`).
  - There is no version file: Anchorage stores the release tag itself, and SoH and 2ship regenerate their archive after a port version change.
  - Ghostship 3.0.0, PaperBoat 1.0.3 and Lighthouse 1.2.2 ([docs/research/ports-2.md](../docs/research/ports-2.md)): Ghostship and PaperBoat ship `*-Linux.zip` (an AppImage and `gamecontrollerdb.txt`, which their AppImages lack, so it is an extra file; PaperBoat's AppImage is not executable in the zip), Lighthouse a bare `lighthouse.appimage` (with `gamecontrollerdb.txt` inside; 1.1.0 and older were `-Linux.zip`). All three honour `SHIP_HOME`, take only big-endian `.z64` data (raw SHA1, no byte swap), and write `sm64.o2r`, `pm64.o2r` and `bk.o2r` into the data folder. Only Lighthouse uses a ROM path given as an argument on Linux; Ghostship and PaperBoat ignore arguments there and find a `.z64` with a supported SHA1 in their data folder after asking "Generate one now?". Every release asset lists a `sha256:` digest. Accepted ROMs: Super Mario 64 US and JP, Paper Mario US, Banjo-Kazooie US 1.0, US 1.1, PAL and JP.
  - Under gamescope the ports force fullscreen and disable ImGui viewports themselves; their file pickers are unusable in game mode, which is why ROMs are placed before launch.
- **Launching.** `app/src/launcher.gd` builds the child environment from Anchorage's own (`/proc/self/environ`) and starts the port through `/bin/sh`, which unsets and exports the differences, changes to the working directory, sends the output to `launch.log` and `exec`s the port. `OS.create_process` takes neither a working directory nor an environment, and changing Anchorage's own environment around the spawn would race its other threads. Exit is detected by polling `OS.is_process_running` from `Ports._process`.
- The research behind these notes, with the accepted SHA1 list for every port, is in [docs/research/ports.md](../docs/research/ports.md). The catalog is the source of truth for hashes once it exists.

## First launch (found by research, 2026-11)

Every port makes its game files (`.o2r`) from the ROM on the first launch, and asks before it does. The prompts cannot all be answered with a gamepad (research: [docs/research/first-run-extraction.md](../docs/research/first-run-extraction.md), read from source at the release tags, not run on a Deck):

- Shipwright and 2ship2harkinian use ImGui popups, whose gamepad navigation is off by default on Linux. Given the ROM as a command-line argument they extract straight away, with a progress popup and none of the "Generate one now?" prompts. After it they ask `Run SoH?`.
- SpaghettiKart and Starship use `SDL_ShowMessageBox`, which takes mouse and keyboard only (the Deck's trackpad works as a mouse in the default non-Steam layout). SpaghettiKart skips its ROM picker when a valid `.z64` is in its working directory; Starship always shows a picker.
- Ghostship asks twice in ImGui popups ("Generate one now?", then "Found Super Mario 64 (US). Generate game files from it?"); its libultraship never turns on gamepad navigation for popups. PaperBoat asks "Generate one now?" and "ROMs found", extracts, then asks "Run PaperBoat?"; gamepad navigation in its popups needs the `ControlNav` setting, which is off by default. Lighthouse, given the ROM as an argument, extracts without asking and then asks "Run Lighthouse?", as Shipwright does ([docs/research/ports-2.md](../docs/research/ports-2.md)).

## Catalog updates

- The catalog file is `app/data/ports.json` (schema in `app/src/catalog.gd`). It gets a top-level `schema` (the version of this format, 1 today) and `version` (an integer raised whenever the list changes); the app refuses a catalog whose `schema` is higher than it knows, so a future format change never breaks an old app.
- Trust: the fetched catalog comes from this repository over HTTPS, like the app itself. It can name which GitHub repositories to download from, so editing `ports.json` on `main` is a security-relevant act: review it like code. The digest check (`PORT-3`) and the host rules (`PORT-22`) still apply. There is no signature in the MVP.
- Contract additions: `ports.notice() -> String` and the signal `notice_changed`; `info(id).is_new` (bool); `ports.mark_seen(id)`, which the home screen calls when a card gets focus, clears `is_new`; `ports.refresh()` also fetches the catalog. A fetch only ever appends to `list()`, and `notice_changed` fires after it has, so a screen adds cards for the ids it does not show yet. A port that a later catalog drops leaves the list at the next start, never under the user's cursor.
- Checks on a fetched catalog, stricter than on the built-in one (`PORT-19`, `PORT-22`): `schema` and `version` must be positive integers; an entry with a key the app does not know, or an unknown `rom_place` or `launch.cwd`, is skipped as `needs a newer Anchorage`; bad `art` refuses the whole entry instead of being dropped. For every catalog: `id` at most 32 of `a-z 0-9 _ -`; `repo` an ASCII `owner/name` with neither part `.` or `..`; `executable`, `archive` and `extra_files` plain relative paths (parts of `A-Z a-z 0-9 . _ + -`, none starting with `.` or `-`, at most 128 characters); `rom_file` a plain file name ending in `.z64`; `args` at most 16, each of `A-Z a-z 0-9 . _ = : , + -` without `..`; text fields without control characters (`first_run` may hold line breaks) and of bounded length. The launcher passes these as separate `argv` entries to its fixed script (`exec "$@"`), so no catalog value is ever read by a shell as code.
- The catalog fetch keeps its own time in `state.ini` (`[catalog] last_check`) under the same one-hour rule as the update check (`PORT-5`), and runs just before it, so new ports are checked too. A fetch that fails does not count.
- **What a malicious catalog can still do** (adversarial review, 2026-11-24). Whoever can change `ports.json` on `main` (or GitHub's raw host) can:
  - **Run code on every machine that installs or updates.** An entry names the GitHub repo whose release Anchorage downloads and runs; a higher `version` can point an installed port's `repo` at another repo, and its next update installs from there. The `sha256` digest only proves the file is what GitHub lists, not who made it. This is the trust the MVP accepts (no signature): review `repo` changes on `main` like code.
  - **Replace files in an installed port's data folder by name** at its next install or update, through `extra_files` naming something the release contains (a `saves` folder, a config file). Launch only adds missing ones, and the ROM copy never overwrites a file Anchorage did not write (`PORT-9`).
  - **Hide or confuse ports**: drop uninstalled ports at the next start, change an installed port's `executable` or `asset_suffix` so it shows as not installed (its files stay), or give a port misleading text (plain text only: no control, zero-width or bidi characters, bounded lengths, and no input fields to phish into).
  - **Hand a port its own arguments** (`args` of letters, digits and `. _ = : , + -`: no paths, URLs, spaces or shell characters) and **the user's ROM** (a fetched entry may list another game's hashes, so the ROM is copied to its data folder and maybe passed to it).
  - **Use up GitHub's unauthenticated API limit** (60 an hour) with up to 64 ports, so update checks show `Offline`; and fetch images from the SteamGridDB CDN for the decoders (`ART-4` limits).
  - **Pin a huge `version`** so later corrections replace nothing in this session; the next start reads the then-cached lower version and recovers, but the "needs a newer Anchorage" line stays silent up to that version.
  It cannot: name a host other than github.com release downloads, the SteamGridDB CDN and the API; write outside a port's folder (`..`, absolute and hidden paths refused); reach a shell (`launcher.gd` runs a fixed `/bin/sh` script and passes values as `argv` through `OS.create_process`, which is `fork`/`execvp`; `OS.execute` with an output array would go through `popen` and is never used); change `state.ini` beyond the new-port ids (validated as ids on read); grow past 256 KiB or 64 ports; or break the app with a format change (`schema`).
- **Test hook.** `ANCHORAGE_CATALOG_URL` replaces the catalog URL, for tests and development only. It takes an `https://raw.githubusercontent.com/` URL or a plain `http://127.0.0.1:<port>/` one; anything else is ignored. How to add a port, and test it this way: [docs/adding-a-port.md](../docs/adding-a-port.md).
