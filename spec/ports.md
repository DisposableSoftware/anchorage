# Ports

How Anchorage finds, installs, updates, launches and removes the HarbourMasters ports. Facts about each port (asset names, ROM lookup, environment variables) come from reading the ports' releases and source; the research is summarised in the implementation notes. Where a fact could not be run on a real machine, it says so.

## Implementation notes

- **Service contract.** `app/src/ports.gd` (`Ports`, a `Node`) is created by `main.gd` and handed to screens. Screens read `ports.list() -> Array` of port ids in catalog order and `ports.info(id) -> Dictionary` with these keys: `id`, `name`, `game`, `description`, `installed` (bool), `installed_version`, `latest_version` (empty when unknown), `update_available` (bool), `offline` (bool), `rom` (`{found: bool, label: String, path: String, wanted: Array[String]}`; `wanted` names the game versions the port accepts), `busy` (`{action: "install"|"update"|"remove"|"launch"|"scan"|"", progress: float, detail: String}`; `progress` is 0..1 or -1 when unknown), `running` (bool), `art` (the cover art as a `Texture2D`, or `null` while there is none: `art.md`), `error` (`""` or a `Could not <verb> "<name>"` message with detail). Screens call `ports.install(id)`, `update(id)`, `remove(id)`, `launch(id)`, `cancel(id)`, `refresh()` (updates and ROM rescan) and `dismiss_error(id)`. `Ports` emits `changed(id)` whenever `info(id)` changes, and `launched(id)` and `exited(id)`. A `ports_fake.gd` with the same interface and fixed demo data serves screenshots and UI tests.
- **Layout under `user://`** (`$XDG_DATA_HOME/anchorage/`): `ports/<id>/current/`, `previous/`, `download/`, `data/`. While an install runs, `download/` holds the downloaded asset and the unpacked new version (`download/staging/`), which is renamed to `current/` at the end. `cleanup_stale` also puts `previous/` back as `current/` when a kill came between the two renames of a swap.
- **Catalog schema** (`app/data/ports.json`, documented in the header of `app/src/catalog.gd`). One object per port in `ports`:
  - `id`, `name`, `game`, `description`, `repo` (`owner/name`), `asset_suffix` (matched without case against the asset name).
  - `archive`: the generated archive names; the port counts as extracted when any exists.
  - `launch`: `executable` (path inside `current/`; a bare AppImage is saved under this name), `cwd` (`data` or `current`), `args`.
  - `extra_files`: paths of files or folders inside the unpacked release that install copies into `data/` (`PORT-10`), and launch copies again when missing (`PORT-9`).
  - `rom_place` (`data_dir` or `cwd`, the launch working directory), `rom_file` (name of the written big-endian ROM, ending in `.z64`) and `roms`: a list of `{label, sha1}` in priority order (`ROM-7`). A bad entry is dropped with a warning, never a crash.
- **Update checks.** The automatic check at start runs when `[ports] check_updates` is not `false` and the last successful check is at least one hour old (or in the future, or missing). The `refresh` binding is the user asking, so it always checks. A check that no port answered does not count as a check. Release downloads are redirected to a CDN: `http.gd` follows redirects by hand, downloads and API calls alike, and accepts only https hops on GitHub's hosts whose host part is a plain name (`PORT-13`). Downloads are polled from the main loop, not on `HTTPRequest`'s thread: that thread blocks in a socket read, and cancelling a stalled download (which joins it) froze the app. A repo that GitHub has moved is followed for the API call only, so the catalog must name the current `repo`, or the asset URL is refused.
- **What the research found** (read from the latest releases, 2026-11; nothing below was run on a Deck):
  - Shipwright 9.3.1 ships a bare `.appimage`; 2ship2harkinian 5.0.1, Starship v2.0.0 and SpaghettiKart 1.0.0 ship `*-Linux.zip` or `spaghetti-linux.zip` holding an `.appimage` and extra files. Codenames change per minor version, so match on a suffix. The AppImages need `libfuse.so.2` or `APPIMAGE_EXTRACT_AND_RUN=1`.
  - No port reads a ROM from a zip. SoH and 2ship byte-swap `.v64` and `.n64`; Starship and SpaghettiKart need big-endian `.z64`. So Anchorage always writes `.z64`.
  - SoH and 2ship scan their data folder for ROMs and treat every command-line argument as a ROM path. SpaghettiKart scans the current directory for `*.z64`. Starship v2.0.0 only has a file picker for the ROM and reads `config.yml` and `assets/` from the current directory and writes `sf64.o2r` there, so its catalog entry copies both into the data folder (`extra_files`) and runs it there (`cwd: data`). A fully unattended first extraction is not possible for Starship, and all ports may show a popup. The catalog states, per port, how the ROM is handed over; Starship's first run is a known gap (`PORT-9`).
  - `SHIP_HOME` sets the data folder on Linux for all four. Generated archives: `oot.o2r` (and `oot-mq.o2r`), `mm.o2r`, `sf64.o2r`, `mk64.o2r`.
  - Asset digests (one unauthenticated `releases/latest` call per repo, 2026-11-23): Shipwright 9.3.1, 2ship2harkinian 5.0.1 and SpaghettiKart 1.0.0 list `"digest": "sha256:<64 hex>"` for every asset; Starship v2.0.0 (May 2025, older than GitHub's digests) lists `"digest": null`, so for it only the size is checked. Each release has exactly one asset matching its suffix (`SoH-Dewey-Bravo.appimage`, `2Ship-Battler-Bravo-Linux.zip`, `Starship-Barnard-Alfa-Linux.zip`, `spaghetti-linux.zip`).
  - There is no version file: Anchorage stores the release tag itself, and SoH and 2ship regenerate their archive after a port version change.
  - Under gamescope the ports force fullscreen and disable ImGui viewports themselves; their file pickers are unusable in game mode, which is why ROMs are placed before launch.
- **Launching.** `app/src/launcher.gd` builds the child environment from Anchorage's own (`/proc/self/environ`) and starts the port through `/bin/sh`, which unsets and exports the differences, changes to the working directory, sends the output to `launch.log` and `exec`s the port. `OS.create_process` takes neither a working directory nor an environment, and changing Anchorage's own environment around the spawn would race its other threads. Exit is detected by polling `OS.is_process_running` from `Ports._process`.
- The research behind these notes, with the accepted SHA1 list for every port, is in [docs/research/ports.md](../docs/research/ports.md). The catalog is the source of truth for hashes once it exists.

## First launch (found by research, 2026-11)

Every port makes its game files (`.o2r`) from the ROM on the first launch, and asks before it does. The prompts cannot all be answered with a gamepad (research: [docs/research/first-run-extraction.md](../docs/research/first-run-extraction.md), read from source at the release tags, not run on a Deck):

- Shipwright and 2ship2harkinian use ImGui popups, whose gamepad navigation is off by default on Linux. Given the ROM as a command-line argument they extract straight away, with a progress popup and none of the "Generate one now?" prompts. After it they ask `Run SoH?`.
- SpaghettiKart and Starship use `SDL_ShowMessageBox`, which takes mouse and keyboard only (the Deck's trackpad works as a mouse in the default non-Steam layout). SpaghettiKart skips its ROM picker when a valid `.z64` is in its working directory; Starship always shows a picker.
