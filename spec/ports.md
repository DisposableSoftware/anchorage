# Ports

How Anchorage finds, installs, updates, launches and removes the HarbourMasters ports. Facts about each port (asset names, ROM lookup, environment variables) come from reading the ports' releases and source; the research is summarised in the implementation notes. Where a fact could not be run on a real machine, it says so.

## Requirements

| ID | Requirement | Status | Verified by |
|----|-------------|--------|-------------|
| `PORT-1` | The catalog `app/data/ports.json` lists every port as data: `id`, `name`, `game`, `description`, GitHub `repo`, release asset pattern, how to launch it, which ROM hashes it accepts and where it wants the ROM placed. Adding a port is adding an entry, with no code change (`PROD-13`). | planned | `test_catalog` (every entry has every field; ids are unique; the four launch ports are present) |
| `PORT-2` | The latest release of a port is read from the GitHub API (`releases/latest` of the catalog repo, unauthenticated), ignoring prereleases. The Linux asset is the one whose name matches the catalog's pattern (a suffix, because codenames change with each minor version). A network or API failure leaves the last known state and shows the port as offline, never as an error that blocks playing. | planned | `test_releases` (fake HTTP responses: asset choice, no match, failure) |
| `PORT-3` | Install downloads the asset into `user://ports/<id>/download/`, checks that the size matches the release, unpacks a zip (rejecting any entry with an absolute path or `..`) or keeps a bare AppImage, marks the AppImage executable, and only then moves the result to `user://ports/<id>/current/`. A cancelled, failed or killed install never leaves a partial `current/`. | planned | `test_installer` (local files and fake HTTP: success, bad size, hostile zip entry, cancel) |
| `PORT-4` | Downloads report progress (bytes done and total) and can be cancelled, and never block the main loop (`HTTPRequest` with `download_file`). | planned | `test_installer`; manual (screenshot of the progress state) |
| `PORT-5` | Anchorage checks for updates once at start in the background when `[ports] check_updates` is `true`, and on `refresh` (`HOME-6`), at most once per hour automatically. The check stores the latest tag and the time in `state.ini`. A port is `update available` when the latest tag differs from the installed one. | planned | `test_releases`; `test_state` |
| `PORT-6` | Update downloads the new version next to the old one and swaps only when it is complete. The old version moves to `user://ports/<id>/previous/` and is deleted once the new version has been launched and has kept running for 10 seconds. If the update fails at any step, the old version stays in `current/`. | planned | `test_installer` (swap, failure leaves the old one, previous cleanup) |
| `PORT-7` | Remove deletes `user://ports/<id>/current/` and `previous/` and clears the installed version. It never deletes the port's data folder `user://ports/<id>/data/` (saves, config, generated `.o2r` archives). | planned | `test_installer` |
| `PORT-8` | Launch runs the port as a child process from `current/` with `SHIP_HOME` set to the port's data folder and `APPIMAGE_EXTRACT_AND_RUN=1` (AppImages work without FUSE), in the working directory the catalog names, and with the arguments the catalog names. Anchorage polls for the process ending without blocking. | planned | `test_launcher` (a fake port script: environment, working directory, exit detection); manual (a real port) |
| `PORT-9` | Before launch, when the matched ROM exists (`ROM-3`) and the port's generated archive (catalog `archive`, e.g. `oot.o2r`) is missing from the data folder, Anchorage writes the ROM there as a big-endian `.z64` (`ROM-8`) where the catalog says the port looks for it. Once the archive exists, any ROM copy Anchorage placed is deleted. | planned | `test_launcher` (placement and cleanup with a fake ROM) |
| `PORT-10` | When the catalog lists extra files for a port (the `gamecontrollerdb.txt` that Starship and SpaghettiKart do not bundle), install copies them from the unpacked release into the data folder. | planned | `test_installer` |
| `PORT-11` | What Anchorage remembers (installed version, latest known tag, last check time, ROM scan cache) is written to `$XDG_STATE_HOME/anchorage/state.ini`, atomically (write a temp file, then rename). A missing or broken file means nothing is remembered, not a crash. | planned | `test_state` |
| `PORT-12` | At most one install, update or launch runs at a time per port, and one download at a time overall. Leftover `download/` folders from a killed run are deleted at start. | planned | `test_ports` |
| `PORT-13` | Anchorage downloads only `https://github.com/` release assets of the repos named in the catalog, and runs nothing except the port's own executable. | planned | `test_releases` (a foreign URL or host is refused) |
| `PORT-14` | `Ports` is the one object screens talk to (see the implementation notes): the UI never touches the network, the disk layout or processes itself. | planned | `test_ports`; `test_spec` |

## Implementation notes

- **Service contract.** `app/src/ports.gd` (`Ports`, a `Node`) is created by `main.gd` and handed to screens. Screens read `ports.list() -> Array` of port ids in catalog order and `ports.info(id) -> Dictionary` with these keys: `id`, `name`, `game`, `description`, `installed` (bool), `installed_version`, `latest_version` (empty when unknown), `update_available` (bool), `offline` (bool), `rom` (`{found: bool, label: String, path: String, wanted: Array[String]}`; `wanted` names the game versions the port accepts), `busy` (`{action: "install"|"update"|"remove"|"launch"|"scan"|"", progress: float, detail: String}`; `progress` is 0..1 or -1 when unknown), `running` (bool), `error` (`""` or a `Could not <verb> "<name>"` message with detail). Screens call `ports.install(id)`, `update(id)`, `remove(id)`, `launch(id)`, `cancel(id)`, `refresh()` (updates and ROM rescan) and `dismiss_error(id)`. `Ports` emits `changed(id)` whenever `info(id)` changes, and `launched(id)` and `exited(id)`. A `ports_fake.gd` with the same interface and fixed demo data serves screenshots and UI tests.
- **Layout under `user://`** (`$XDG_DATA_HOME/anchorage/`): `ports/<id>/current/`, `previous/`, `download/`, `data/`.
- **What the research found** (read from the latest releases, 2026-11; nothing below was run on a Deck):
  - Shipwright 9.3.1 ships a bare `.appimage`; 2ship2harkinian 5.0.1, Starship v2.0.0 and SpaghettiKart 1.0.0 ship `*-Linux.zip` or `spaghetti-linux.zip` holding an `.appimage` and extra files. Codenames change per minor version, so match on a suffix. The AppImages need `libfuse.so.2` or `APPIMAGE_EXTRACT_AND_RUN=1`.
  - No port reads a ROM from a zip. SoH and 2ship byte-swap `.v64` and `.n64`; Starship and SpaghettiKart need big-endian `.z64`. So Anchorage always writes `.z64`.
  - SoH and 2ship scan their data folder for ROMs and treat every command-line argument as a ROM path. SpaghettiKart scans the current directory for `*.z64`. Starship v2.0.0 only has a file picker for the ROM and reads `config.yml` and `assets/` from the current directory: it must run with its unpacked folder as the working directory. A fully unattended first extraction is not possible for Starship, and all ports may show a popup. The catalog states, per port, how the ROM is handed over; Starship's first run is a known gap (`PORT-9`).
  - `SHIP_HOME` sets the data folder on Linux for all four. Generated archives: `oot.o2r` (and `oot-mq.o2r`), `mm.o2r`, `sf64.o2r`, `mk64.o2r`.
  - There is no version file: Anchorage stores the release tag itself, and SoH and 2ship regenerate their archive after a port version change.
  - Under gamescope the ports force fullscreen and disable ImGui viewports themselves; their file pickers are unusable in game mode, which is why ROMs are placed before launch.
- The research behind these notes, with the accepted SHA1 list for every port, is in [docs/research/ports.md](../docs/research/ports.md). The catalog is the source of truth for hashes once it exists.
